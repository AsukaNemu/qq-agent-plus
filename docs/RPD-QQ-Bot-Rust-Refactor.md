# QQ Bot Rust 重构项目 RPD

**文档类型**：需求与技术设计文档

**项目名称**：QQ Bot Rust 重构

**版本**：v0.3

**日期**：2026-10-02

**当前目标平台**：原生 macOS，优先 Apple Silicon

**协议端**：继续使用 NapCat，不重写 QQ 登录与 QQ 协议

---

## 1. 项目概述

将现有基于 Node.js、Python、NapCat 和多个 JSON/SQLite 状态文件的 QQ Bot 重构为一个低内存、低耦合、可模块化扩展的 macOS 原生程序。

重构后的核心业务进程使用 Rust 实现，NapCat 继续作为独立的 QQ 协议适配端。前端作为静态管理控制台，由 Rust 后端提供 API 和静态资源；最终切换后不再需要 Node.js 常驻运行时。现有 Python 代理只有在其调用路径已被替代并完成对照测试后才退出运行链路。

目标不是重新实现 QQ 协议，而是把协议层和机器人业务核心彻底分离。

---

## 2. 当前问题

当前系统主要由以下部分组成：

```text
QQ/NapCat
   ↓ OneBot
Node.js 后端
   ├── 消息处理
   ├── LLM 调用
   ├── 记忆系统
   ├── SQLite/JSON 数据
   ├── 管理 API
   └── 前端控制台
        ↓
Python API 代理（可选）
```

现有风险：

- 业务逻辑、控制台 API、服务启动逻辑集中在较大的 Node 入口中。
- 部分功能容易直接依赖 OneBot、数据库、全局配置或其他功能模块。
- 历史消息、媒体、任务状态容易出现多份缓存。
- 修改代码通常需要重启整个 Node 后端。
- Node.js 和 Python 运行时增加常驻进程数量。
- 功能增加后，模块之间的依赖关系难以控制。

2026-10-02 的一次现场内存采样约为：

| 部分 | RSS |
|---|---:|
| QQ/NapCat 进程 | 约 527 MB |
| Node.js 后端 | 约 110 MB |
| Python 代理 | 约 16 MB |
| 实际 Bot 运行链路 | 约 653 MB |

以上为单次 RSS 快照，QQ/NapCat、缓存和当前会话会影响结果；正式对比必须按第 14 节的相同负载与采样方法重测。

## 3. 项目目标

### 3.1 总体目标

建立一个 Rust 模块化单体后端：

- NapCat 继续负责 QQ 协议。
- Rust 负责所有机器人业务。
- 所有功能按模块组织。
- 历史消息和长期状态优先存储在 SSD 上，不长期驻留内存。
- 新二进制编译完成后的后端切换与恢复控制在 10 秒内。
- 前端不因后端短暂重启而必须刷新页面。
- 最终运行链路不依赖 Node.js；Python 代理只有在功能替代完成后才退出。

### 3.2 目标指标

| 指标 | 目标 |
|---|---|
| Rust 后端空闲 RSS | 目标 ≤ 40 MB |
| Rust 后端典型负载 RSS | 目标 ≤ 80 MB |
| 编译完成后切换至服务恢复 | ≤ 10 秒 |
| 后端恢复后前端显示最新状态 | ≤ 2 秒 |
| 消息队列 | 必须有界，默认上限 256 条 |
| LLM 并发 | 默认 2～4 个，可配置 |
| 历史消息加载 | 按需分页，禁止全量加载 |
| 生产常驻后端 | 一个 Rust 进程 |

QQ/NapCat 的内存不纳入 Rust 后端内存指标，因为协议端不在本次重构范围内。

RSS 数字是设计预算，需在第一版原型按第 14 节验证；若超过预算，先定位缓存、队列、SQLite、网络连接或媒体处理的贡献，再决定是否调整目标，不能仅凭语言选型保证达标。

## 4. 非目标

本期不做以下事项：

- 不重写 QQ 登录、QQ 协议或 NapCat。
- 不实现 Linux 版本。
- 不一开始引入动态 Rust `.dylib` 插件系统。
- 不一开始拆成多个常驻微服务。
- 不要求真正的零停机代码热替换。
- 不在 Rust 进程启动时加载大型本地 ASR、视觉或语言模型。
- 不强制把前端做成常驻桌面应用。

## 6. 技术选型

### 6.1 后端

- Rust stable
- Tokio：异步运行时
- Axum：管理 API 和静态资源服务
- `tokio-tungstenite`：OneBot WebSocket
- `rusqlite`：SQLite 访问
- Serde：配置和协议数据序列化
- Tracing：日志与诊断
- Clap：命令行管理工具
- `thiserror`：错误类型

### 6.2 前端

前端页面完全重新制作，不沿用当前控制台的页面布局和视觉样式。运行时静态视觉资源及核心动效实现取自固定版本的 [RhineLabUI](https://github.com/LBEILC/RhineLabUI)，采用 TypeScript + Vite。档案阵列、卡片抽取和模型查看使用 Three.js；普通表单、日志和消息阅读保持 DOM 交互。三维场景按页面加载，不在后台常驻渲染。

前端编译后只输出静态文件，生产环境不运行 Node.js。前端由 Rust API 提供，浏览器按需打开，不作为 Bot 常驻进程。

本项目的前端实现不使用前端 skill、Product Design skill 或其他自动生成的前端设计流程；所有页面、动效和组件按照本 RPD 中的视觉与交互规范直接实现。

### 6.3 服务管理

使用 macOS `launchd`：

- 登录时启动
- 异常退出自动重启
- 代码升级时由 `qqbotctl` 执行受控重启
- 日志输出到独立文件

## 7. NapCat 适配要求

NapCat 适配层是唯一允许接触 OneBot 原始 JSON 的模块。

### 7.1 连接

默认使用：

```text
WebSocket：ws://127.0.0.1:3001/onebot/v11/ws
HTTP：      http://127.0.0.1:3000
```

具体地址、Token 和超时时间必须从配置读取，不允许散落在业务模块中。

### 7.2 适配层职责

- WebSocket 连接和重连
- OneBot 事件解析
- OneBot API 请求
- 鉴权
- 请求超时
- API 错误归一化
- NapCat 特有扩展接口隔离
- 健康检查

### 7.3 内部事件

业务核心只接收统一事件：

```rust
struct IncomingMessage {
    message_id: String,
    conversation_id: String,
    sender_id: String,
    is_group: bool,
    segments: Vec<MessageSegment>, // 文本、@、回复、图片、语音等
    timestamp: i64,
}
```

业务模块不得直接依赖 `post_type`、`group_id`、`raw_message` 等 OneBot 原始字段。NapCat 扩展字段若业务确实需要，先添加有明确语义的内部类型，再由 adapter 映射；未知消息段保留可追踪的降级信息，不静默丢弃。

### 8.2 功能模块接口

功能模块接收内部事件和只读查询能力，返回命令；以下是契约示意，具体 Rust async trait 形式在实现时确定：

```text
Feature::on_event(Event, ReadOnlyContext) -> Vec<Command>
Command::SendMessage | UpdateMemory | ScheduleTask | RecordIncident | ...
```

`ReadOnlyContext` 按功能最小授权提供会话查询、配置快照和模型调用能力。模块不持有 `MessageGateway`、SQLite 写连接或 NapCat 客户端。统一的命令执行器负责校验、持久化、限频、outbox 记账与最终发送；一条事件的命令按确定顺序执行并留审计记录。

功能模块不得：

- 直接访问 NapCat WebSocket
- 直接拼接 OneBot JSON
- 直接修改其他模块的数据库表
- 使用无限增长的全局缓存
- 创建没有上限的后台任务
- 依赖另一个功能模块的私有实现
- 绕过统一命令执行器直接发送消息或更改持久状态

模块之间通过事件、命令和接口交互。

## 9. 数据与内存策略

### 9.1 内存中只保留

- 当前正在处理的一条消息
- 有界队列中的消息 ID
- 当前会话最近若干条上下文
- 当前运行中的有限数量 LLM 请求
- 小型配置缓存

### 9.2 SSD 中保存

- 全部历史消息
- 对话摘要
- 长期记忆
- 出站消息状态
- 定时任务
- 配置与功能开关
- 图片、语音和其他媒体文件

### 9.3 消息处理流程

```text
收到 OneBot 事件并按会话+OneBot message_id 去重
    ↓
事务写入 SQLite inbox，记录原始事件的必要追踪字段
    ↓
内存队列只保存消息 ID
    ↓
Worker 查询最近上下文
    ↓
调用 LLM
    ↓
由命令执行器写入 SQLite outbox
    ↓
调用 NapCat 发送
    ↓
更新发送状态
```

### 9.4 SQLite 要求

- 使用 WAL
- 所有表通过 migration 管理
- 历史消息按会话和时间建立索引
- 查询必须分页或带 `LIMIT`
- 媒体不以长期 Base64 存储
- inbox 使用唯一键去重，租约到期后可恢复处理；同一会话最多一个有效处理租约
- outbox 支持 `pending/sending/sent/failed/unknown/reconciled_sent/reconciled_failed`
- 发送超时、连接重置等无法确定对方是否收到的结果进入 `unknown`，禁止自动重发；提供管理员核对与解除阻塞的操作
- 只有能证明请求未被 NapCat 接收的失败才允许自动重试，并记录尝试次数
- inbox、任务租约和 outbox 迁移时保留旧系统可观察的状态语义，避免升级后重复回复
- 数据库连接数量受限

### 10.3 重启要求

代码更新期间旧版本继续运行。新版占用相同的固定端口，因此旧版运行时只做**离线预检**，不能把离线预检称为线上健康检查。

```text
旧版运行
    ↓
在独立构建目录编译新版并保留旧二进制
    ↓
离线预检：校验可执行文件、配置和数据库快照上的兼容迁移；不占 3210 端口，不连接生产 NapCat，不写生产数据库
    ↓
记录切换起点；旧版停止接收新消息并有界等待/取消在途任务
    ↓
旧版退出并关闭 WebSocket、API 端口
    ↓
原子切换版本指针，由 launchd 启动新版
    ↓
检查 `/api/health`、OneBot 已连接和核心 Worker 已就绪
    ↓
记录切换终点；前端自动重连并获取快照
```

允许切换期间不接收消息。**10 秒计时范围**为“旧版开始停止接收新消息”至“新版 API、NapCat 连接和核心 Worker 均就绪”；编译与离线预检发生在旧版仍运行期间，不计入停机时间。前端在新版就绪后 2 秒内显示最新快照。因外部 NapCat 不可用导致的恢复失败单独记录，不伪称达到时限。

时间预算：旧版停收与在途任务有界处理 ≤ 2 秒，退出与版本指针切换 ≤ 1 秒，新版启动及 NapCat 重连 ≤ 5 秒，真实健康检查 ≤ 2 秒。超时即进入回滚流程，并记录每段耗时；不能通过无限等待 LLM 请求来满足“优雅退出”。

失败回滚：若新版在 10 秒内未通过真实健康检查，`qqbotctl` 恢复旧版本指针并启动旧版，记录失败原因和实际中断时间。可回滚版本必须与当前数据库 schema 兼容；上线迁移优先采用先扩展、后清理的两阶段方式。涉及不可逆数据迁移时，先生成 SQLite 一致性备份并单独安排维护窗口，不纳入普通 10 秒更新承诺。

本节的 10 秒承诺适用于 Rust 版本之间的日常升级和 Debug 重启。首次从 Node 切换到 Rust 需要执行数据迁移和对账，按第 13 节单独验收并记录维护时间。

### 10.4 前端恢复

前端不因后端短暂重启而刷新页面：

- 保留最近一次状态
- API/SSE 断开后自动重连
- 重连成功后请求 `/api/snapshot`
- 显示短暂的“正在重连”状态
- 重新连接后及时更新日志、状态和任务列表
- 状态快照携带单调递增版本号；SSE 事件携带事件 ID，客户端发现版本缺口时重新拉取快照

## 11. API 设计

### 11.1 管理 API

```text
GET    /api/health
GET    /api/status
GET    /api/snapshot
GET    /api/config
PATCH  /api/config
GET    /api/messages
GET    /api/tasks
POST   /api/tasks/:id/cancel
POST   /api/reload-config
POST   /api/restart
GET    /api/events       # SSE
GET    /api/outbox/unknown
POST   /api/outbox/:id/reconcile
```

### 11.2 原则

- 前端只调用 Rust API。
- 前端不直接访问 NapCat。
- 前端不直接读 SQLite。
- API 返回稳定的业务数据结构。
- 密钥只返回掩码，不返回真实值。
- `/api/events` 与普通 API 使用相同的本地会话认证；浏览器 EventSource 依靠同源会话 Cookie，不把长期 Token 放在 URL 查询参数中。远程访问若将来启用，登录、会话及写操作保护另行设计并验收。

## 12. 安全要求

- 管理 API 默认只监听 `127.0.0.1`。
- 需要远程访问时必须启用 Token。
- 模型密钥优先存储在 macOS Keychain。
- 配置文件权限限制为当前用户可读。
- 日志中不得输出 Token、Cookie 和完整请求头。
- NapCat Token 不进入前端。
- 所有外部 HTTP 请求设置超时和响应体大小上限。

### 阶段 6：切换生产

- 新旧系统并行时 Rust 端只读/观察；只有 Node 端连接实际发送链路、写入生产数据库。Rust 端使用事件回放或独立快照，禁止双端同时发送或写生产数据。
- 对比回复、消息落库和任务状态。
- 生产写入权只能由一个后端持有；首次切换先停 Node，获取最终一致性快照并导入最后增量，对账通过后再启动 Rust。该首次迁移不套用第 10.3 节的 10 秒日常升级时限。先用小范围白名单验证，再逐步放量。
- 首次切换时 Rust 使用迁移后的独立数据目录；Node 的原数据目录保留为回滚快照。回滚不让旧 Node 直接打开 Rust 改写后的数据库，切换期间的消息差异另行对账。
- 保留 Node 版本及其数据快照作为回滚版本。
- 连续稳定运行且完成下方矩阵全部必需项后，移除 Node 常驻依赖；Python 代理按独立替代验证结果处理。

阶段 0 以实际运行配置为准确认每项是否启用。**已启用的功能和写入路径必须在正式生产切换前达到等价行为**；未启用项可延期，但必须记录“延期”及其数据保留方式。下表为最低盘点范围：

| 现有领域或入口 | Rust 目标模块 | 最低对照用例 |

| `core/store`、`sessions`、会话线程 | inbox、outbox、session store | 租约恢复、会话接续、去重、发送结果未知后的人工核对 |
| `llm`、providers、prompt、persona | llm adapter、prompt service | 当前启用供应商、模型选择、密钥绑定、上下文和工具调用 |
| `memory`、全局人物记忆 | memory feature、memory store | 会话记忆读取、写入、摘要与禁用后数据保留 |
| `identity`、好友请求 | identity feature | QQ 身份合并、好友申请审批与历史记录 |
| relationship、incident、slang 等 pilot | 独立 feature | 当前启用功能的开关、状态和异常台账 |
| stickers、face、poke、媒体发送 | asset feature、outbox | 文本/图片/语音/贴纸发送与未知结果处理 |
| ASR、vision、图片降采样 | media/vision adapter | 音频转写、图片识别、大小限制和失败降级 |
| QZone、daily moments、主动消息 | qzone、scheduler feature | 读取、发帖/互动、定时触发和重复任务防护 |
| tools、web search | tool executor | 工具权限、超时、取消和调用结果归档 |
| pricing、usage、token saver | usage feature | 用量记录、价格计算和配置生效值 |
| console API、配置、自动更新、运维脚本 | API、qqbotctl、launchd | 管理操作、备份、升级、回滚和前端状态一致性 |
| `workbuddy2api-hub` Python 代理 | 保留或独立替代 | 所有依赖代理的请求类型和错误处理一致后才能停用 |

任何现有功能的删除或行为变更都要单列决策记录；“尚未迁移”不能被解释为“重构后不需要”。

### 数据迁移与回滚矩阵

| 当前数据 | 迁移要求 |
|---|---|
| `messages.sqlite` 及 WAL/SHM | 使用 SQLite 一致性备份；核对消息、租约、线程、outbox 及未知发送状态 |
| `identity-pilot.sqlite`、`relationship-pilot.sqlite`、`incident-pilot.sqlite` | 分库盘点 schema、主键和关联关系；导入后逐表核对数量和抽样记录 |

## 14. 验收标准

验收分为两个门槛：**原型门槛**验证最小收发链路与技术预算；**生产切换门槛**要求第 13 节所有当前启用功能及第 17.4 节全部八个前端页面通过对照。第 16 节的第一版交付物是原型，不得据此直接停用 Node 后端。

### 功能验收

- 可以连接当前 NapCat。
- 可以接收私聊和群聊消息。
- 可以发送文本、图片和语音消息。
- 可以调用现有模型服务。
- 历史消息可以查询，不需要全量加载到内存。
- 记忆、贴纸和定时任务可以独立开关。
- 前端可以查看状态、日志、消息和配置。
- 第 13 节每项已启用功能都有一条以上新旧行为对照记录，输入样例和期望结果可复现。
- 所有数据迁移项均有计数、抽样和失败清单，旧数据快照可以用于回滚。

### 稳定性验收

- NapCat 断线后自动重连。
- LLM 超时不会阻塞其他会话。
- 单个功能错误不会导致整个进程崩溃。
- 数据库写入失败有明确日志和重试策略。
- 重启后未完成的 outbox 任务状态可恢复。
- 未知发送结果不会自动重试，管理员可以查看、核对和解除对应会话阻塞。
- 连续执行 10 次受控切换，均在 10 秒内恢复 API、NapCat 连接和核心 Worker；故意部署无法启动的版本时旧版可自动恢复。

### 性能验收

- Rust 后端空闲 RSS 目标不超过 40 MB。
- Rust 后端典型负载 RSS 目标不超过 80 MB。
- 消息队列不会无限增长。
- 单个媒体文件处理不导致长期内存增长。
- 稳定负载下运行 24 小时，扣除前两小时预热后，RSS 不出现持续单向增长；超标时记录时间序列与分配来源。

### 性能与恢复测试方法

- 在同一台 Apple Silicon Mac、相同 QQ/NapCat、相同配置和外部依赖下分别测 Node 与 Rust；记录机器内存、系统版本、进程版本及测试时间。
- 单独采集 `qqbotd` RSS、QQ/NapCat RSS、浏览器进程内存和整机内存压力；不把 QQ/NapCat 或前端 WebView 的内存算进 Rust 后端指标。
- 空闲场景：NapCat 已连接、控制台关闭，预热 10 分钟后连续采样 30 分钟。
- 典型场景：根据切换前至少 7 天日志的消息量与媒体比例回放，维持 30 分钟；记录 RSS 中位数、95 分位和峰值。
- 峰值场景：覆盖消息队列上限、并发 LLM 请求、图片/语音处理；记录排队、拒绝/降级行为和峰值 RSS，不以典型负载预算判定峰值。
- 24 小时场景：固定可复现负载，按分钟采样 RSS；记录 SQLite 页缓存、任务队列和媒体缓存变化。
- 恢复场景：新版已编译和离线预检，记录停收消息、旧进程退出、新进程启动、API 就绪、NapCat 连接、Worker 就绪、前端快照完成各时间点；以第 10.3 节定义的起止点判定 10 秒目标。

## 15. 风险与应对

| 风险 | 应对方式 |
|---|---|
| Rust 初期开发速度较慢 | 先迁移最小链路，不一次性重写全部功能 |
| OneBot 实现存在差异 | 只在 NapCat adapter 中兼容差异 |
| 重启期间消息丢失 | 明确接受短暂不接收；重要任务使用 inbox/outbox |
| LLM 或媒体任务启动慢 | 按需加载，必要时独立 Worker |
| SQLite 写入冲突 | 单写入队列，限制连接数 |
| 功能模块互相依赖 | 通过事件和 ports 通信，禁止跨模块访问私有实现 |
| Rust 版本升级造成兼容问题 | 固定 toolchain，保留锁文件和回滚二进制 |

## 16. 第一版交付物

第一版是技术原型，不替代正在运行的 Node 后端。原型通过事件回放与模拟网关测试发送；如需连接生产 NapCat，只运行观察模式，不向真实 QQ 发送，也不写生产数据库。交付：

```text
qqbotd
├── Rust 原生二进制
├── NapCat OneBot WebSocket/HTTP 适配器
├── SQLite 消息存储
├── 基础白名单
├── 基本文本自动回复
├── LLM Provider 接口

├── 前端四个基础页面与自动重连
├── launchd 配置
└── 10 秒内重启验证脚本
```

第一版稳定后，再逐个迁移当前项目中的高级功能。只有第 14 节的生产切换门槛全部通过，才允许停用旧后端。

### 17.1 视觉参考

视觉参考项目：

### 17.4 页面结构

前端采用 RhineLabUI 式终端档案布局；左侧窄轨道承载一级菜单，当前模块内的二级菜单紧贴主工作区显示，表单仅在相应档案详情中出现：

```text
┌──────────────────────────────────────────────┐
│ SYSTEM ID · CONNECTION · TIME · STATUS       │
├──────┬──────────────────────────┬────────────┤
│      │                          │            │
│ 一级 │ 二级菜单 + 主档案工作区   │ 上下文/状态 │
│ 菜单 │  卡片、消息、日志、图表    │ 详情、指标  │
│      │                          │            │
├──────┴──────────────────────────┴────────────┤
│ EVENT STREAM · VERSION · NAPCAT · LATENCY    │
└──────────────────────────────────────────────┘
```

核心页面：

1. **System Terminal**：系统状态、NapCat 连接、模型、任务和最近事件。
2. **Message Archive**：私聊/群聊消息档案、会话时间线和搜索。
3. **Feature Archive**：所有功能模块的启用状态、健康状态和配置入口。
4. **Memory Archive**：人物记忆、群聊记忆、摘要和记忆更新记录。
5. **Model Archive**：模型供应商、模型延迟、Token 用量和失败记录。
6. **Task Archive**：定时任务、主动消息和待处理 outbox。
7. **Asset Archive**：贴纸、图片、语音和媒体资源。
8. **Diagnostics**：日志、异常、连接状态、数据库和版本信息。

#### 一级与二级菜单

一级菜单按管理任务分为六组，二级菜单直达具体工作区：

| 一级菜单 | 二级菜单与路由 | 对应工作内容 |
|---|---|---|
| 总览 | 运行总览 `/overview`；实时事件 `/overview/events` | System Terminal、连接与最近事件 |
| 会话 | 消息档案 `/conversations/messages`；记忆档案 `/conversations/memory`；身份与申请 `/conversations/identity` | Message Archive、Memory Archive、好友与身份记录 |
| 能力 | 功能模块 `/capabilities/features`；模型与用量 `/capabilities/models`；工具与多模态 `/capabilities/tools` | Feature Archive、Model Archive、工具、ASR 与视觉设置 |
| 自动化 | 任务档案 `/automation/tasks`；主动消息 `/automation/proactive`；QZone `/automation/qzone` | Task Archive、计划、主动发言与空间互动 |
| 资源 | 贴纸与媒体 `/assets/library` | Asset Archive、素材状态与预览 |
| 系统 | 诊断 `/system/diagnostics`；全局设置 `/system/settings`；更新与备份 `/system/maintenance` | Diagnostics、连接、日志、版本与运维 |

八个核心页面仍按上方清单验收；身份与申请、工具与多模态、主动消息、QZone、全局设置、更新与备份是对应核心页面内的功能视图，不另起一套布局。菜单项是否可见由功能启用状态决定；已有数据但功能关闭时仍提供只读档案入口。

导航规则：一级菜单始终可见，二级菜单只显示当前一级下的入口；页面内页签用于详情层级，不再增加第三级全局菜单。一级菜单切换保留每组最近访问的二级位置；URL、浏览器前进/后退、面包屑和选中高亮必须同步。后端断线时页面仍可导航已加载内容，写操作置为不可用并说明状态。关键告警在顶栏常驻提示，点击跳转到诊断的对应记录。

### 17.6 动效要求

网页动效必须实际复用或适配 RhineLabUI 的交互语言与动画实现，不得只贴静态贴图或写一个泛用淡入替代。动效服务于 Bot 状态和档案操作，具体要求如下：

| 场景 | RhineLabUI 对应动效 | Bot 中的实际行为 |
|---|---|---|
| 首次进入总览 | 终端文字输入、圆形/标志展开、身份确认及欢迎转场 | 展示本机控制台接入过程；日常短版总时长 ≤ 3 秒，可立即跳过；设置中可手动重播完整演示 |
| 总览与档案入口 | 3D 档案阵列、纵深循环、波纹扩散 | 展示会话、功能、任务的真实卡片；新消息或任务变化触发一次有界波纹，卡片状态来自 API |
| 选中档案 | 卡片抬升、抽取、回位及相邻卡片让位 | 点击或键盘选择会话/功能/任务，抽取后进入对应详情；返回时保持滚动位置和选择状态 |
| 档案详情 | 玻璃层揭示、文档解密/逐层展开 | 展开消息、记忆、模块配置、日志详情；敏感内容仍遵守 API 掩码和权限规则 |
| 数值与状态 | 滚动标题、编号和数字过渡 | 连接状态、延迟、Token 用量、未处理数和任务编号变更时过渡；真实文本始终可复制、可朗读 |
| 资源预览 | 360° 模型查看与焦点切换 | 对适用的 3D 资源提供拖动/键盘旋转与复位；图片、音频、贴纸不强行转成 3D |
| 页面切换 | 线条、遮罩、面板位移和层叠过渡 | 一级/二级菜单切换及详情返回有连续的空间关系，常规面板过渡以 150～300ms 为目标 |

- 开场只在首次访问或用户主动重播时播放；页面刷新、SSE 重连及 Rust 后端重启不得反复播放。跳过开场后直接显示已取得的状态，不阻塞 API 请求和真实操作。
- 用户快速切换菜单时，旧过渡必须取消或收束到新页面，不得排队播放；弹窗、搜索、保存配置等高频操作优先即时响应。
- 消息流和日志流只使用一次性轻量高亮，不自动抢滚动位置，不使用高频闪烁。扫描线、噪点、光晕和音效可作为低强度反馈，默认不自动播放声音。
- 必须提供站内“减少动态效果”开关，并遵循 `prefers-reduced-motion: reduce`；开启后取消开场、波纹、3D 镜头运动和复杂转场，保留明确的状态变化与可操作性。
- 动效不能成为唯一的信息传达方式；焦点位置、加载状态、错误信息和选中态必须有文字或静态标记。键盘操作与辅助技术可以绕过动画直接使用内容。

### 17.7 三维与性能边界

在支持 WebGL 的桌面浏览器上，RhineLabUI 式 3D 档案阵列是总览/档案入口的默认交互，而非仅供演示的可选页面；但它不能拖慢状态展示或扩大 Rust 守护进程内存。

- 初始 HTML、导航、状态卡和最新快照先渲染；3D 引擎、模型、纹理在其后按路由加载。首屏基础静态资源目标为压缩后不超过 2 MB，不含按需 3D/媒体资源。
- 只在当前总览、会话/功能/任务档案入口或 3D 资源查看器激活相应场景；消息阅读、表单编辑、诊断等页面不持续渲染 3D。
- 离开场景、页面隐藏或后台标签页时暂停渲染循环和音效；重复进入可复用有界资源，达到预算时释放纹理、模型和上下文。
- 提供“性能模式”：关闭 3D、粒子、景深和音效，改用保留阵列布局、卡片抽取与状态反馈的轻量 2D 动效。WebGL 不可用或初始化失败时自动进入该模式。
- 前端浏览器进程的内存与 Rust 守护进程分别测量；在目标 macOS 设备上记录普通模式、性能模式、页面隐藏和长时间运行的占用，不把浏览器开销算作后端节省。
- 3D 加载或降级失败不得阻止消息查询、日志、配置修改；给出明确的静态入口和错误提示。

### 17.8 前端实时显示

前端不需要持续刷新整个页面，但需要及时显示后端状态：

- 首次加载请求 `/api/snapshot`。
- 状态、日志和任务变化通过 SSE 推送。
- SSE 断开后自动重连，前端保留最后一次状态。
- 重连成功后重新请求完整快照，避免只依赖增量事件。
- 后端重启期间显示连接状态，不显示空白页。
- 当前消息、任务和日志列表使用分页或窗口化渲染。

### 17.9 前端组件边界

├── terminal/           # 启动、连接和系统总览

### 17.10 前端验收标准

- 当前控制台页面全部重新制作，不保留旧布局作为生产页面。
- 在 1280×800、1440×900、1920×1080 下布局可用。
- 首屏先显示导航与状态，随后加载默认 3D 档案交互；禁用 WebGL 时仍可通过 2D 模式完成相同操作。
- 第 17.6 节七类场景逐一录屏对照固定版本的 RhineLabUI 参考行为，核对启动、阵列波纹、抽取/返回、详情揭示、数字过渡和查看器均为真实可操作效果，而非静态展示。
- 六个一级菜单及全部二级入口能到达有效视图，路由直达、前进/后退、高亮与面包屑一致；八个核心页面和已启用功能的入口无遗漏、无死链，常用功能从一级菜单至详情不超过两次菜单选择。
- 一级菜单在所有工作区保持同一顺序；二级菜单只显示当前分组。窄窗口下允许折叠菜单，但不能隐藏关键状态与告警。
- 后端重启期间页面不自动刷新；后端就绪后 2 秒内恢复最新状态，正常切换总时长目标不超过 12 秒。
- SSE 断线可以自动恢复，恢复后消息、任务和日志状态一致。
- 开场可跳过、不会在后端重连时重播；快速导航无动画堆积；所有复杂动效都可以关闭。
- 键盘可以完成模块切换、搜索、打开详情和返回。
- 文本、日志、消息和状态值可以复制和被辅助技术读取。
- 使用的 RhineLabUI 静态资源和适配的动效源码均能在资源清单中追溯到具体路径、版本和文件哈希。

### 17.11 实现约束

- 本项目不使用前端 skill 或 Product Design skill。
- 本地前端的全部静态视觉文件必须来自 RhineLabUI 仓库，并固定到明确的 Git commit 或快照。
- 不从其他项目、素材站、图标库或临时生成目录引入前端视觉资源。
- 可以复用 RhineLabUI 仓库中的代码、资源和内容；本项目范围限定为本机使用。
- 视觉、交互、组件和动效规范以本 RPD 为准。

### 17.12 RhineLabUI 资源清单与固定方式

前端资源在仓库中按来源快照管理：

```text
ui/vendor/rhinelabui/
├── SOURCE_COMMIT       # RhineLabUI 固定 commit
├── public/assets/      # GLB、纹理和其他运行模型
├── public/audio/       # 交互音效和配乐
├── public/fonts/       # 字体文件
├── public/archives/    # 档案导出内容
├── content/            # 档案数据
├── src/                # 经挑选的动效参考源码或适配基础，不复制整个前端应用
└── source-manifest.json
```

资源清单 `source-manifest.json` 至少记录：

```json
{
  "path": "public/assets/archive-cassette.glb",
  "source": "LBEILC/RhineLabUI",
  "commit": "<pinned-commit>",
  "sha256": "<asset-hash>",
  "used_by": ["archive-viewer"]
}
```

动效适配清单还须记录来源源码、目标组件、改动说明与验证场景。优先核对固定快照中的 `src/boot.ts`、`src/boot-motion.ts`、`src/scene.ts`、`src/archive-loop.ts`、`src/decryption.ts`、`src/document-decryption.ts`、`src/ui-transitions.ts`、`src/model-viewer.ts`；若固定版本中路径变化，以该 commit 的实际文件为准，不伪造来源。上述源码用于提取时序、材质、镜头、状态机和交互逻辑，接入 Bot API 数据后保持模块边界。

构建要求：

- 生产构建只能读取资源清单中的资源。
- 构建前校验来源 commit 和文件哈希。
- 禁止直接跟踪 RhineLabUI `main` 分支作为生产依赖。
- `art/`、`reference/`、`verification/` 等开发资源只有在确实参与前端功能时才打包，不得因为存在于仓库就全部加载。
- 3D、音频和大字体资源必须按需加载，不能因为资源来自 RhineLabUI 就破坏低内存目标。
- 更新 RhineLabUI 资源时必须产生一份新的 manifest 变更记录，并重新执行前端视觉与性能验收。
