# 多人游戏状态机（群游戏主持）设计与实施方案

> 状态：M1 已实现（2026-09-28）——框架 + 数字炸弹 + 谁是卧底，代码在 `src/features/group-game.js`
> 与 `src/features/games/`，开关与配置项见 `CONFIG-EXAMPLES.md` 的 `groupGame` 一节；本文的实现细节
> （插件接口、效果分发、里程碑划分）仍是 M2/M3 的依据。读者：维护者。
> 目标：让机器人在群里**主持需要状态与回合的多人游戏**，
> 把"只有聊天"的观感变成"群里有个会陪你玩的家伙"。
>
> 前置事实：本仓库已有 `dice/random`、`get_group_member_list` 两个小工具与玩法提示词（L0，
> 无状态轻游戏：成语接龙、猜数字、20 问、抽签——模型自己当主持人即可），本方案是它上面的 L1：
> **需要"隐藏信息、轮次、超时、计分"的游戏**（谁是卧底、狼人杀、数字炸弹、猜词比赛等）。

---

## 1. 设计目标与非目标

**目标**

1. 群友自然发起（"来个谁是卧底"）→ 机器人主持完整一局：报名、发身份、轮次推进、判定、结算。
2. 状态机管**规则与真相**，模型管**主持话术与自由判断**——模型不接触它不该知道的信息（例如谁是卧底里
   谁是什么词），真相不进入模型上下文就能天然防"说漏嘴"。
3. 一局可跨多次运行（群消息是逐批唤醒的），也能**跨重启恢复**。
4. 全程可中止、可超时、可被管理员关闭；对群友零学习成本（就用 @ 和普通发言参与）。
5. 复用现有基建：唤醒（`scheduleInitiativeWake`）、发送（`sender`）、消息库（`store.recent`）、
   活跃时段（`time-gate`）、省 Token 上限（`token-saver`）、实验特性规范（`stable-feature-policy`）。

**非目标（本方案不做）**

- 不做**赌博/竞猜下注**类（合规与群规风险）。
- 不做需要账号权限或批量对外动作的玩法（好友申请已退役的教训）。
- 不做实时对局（音游/棋类需要毫秒级同步；QQ 群消息本身是秒级异步）。
- 不做跨群联赛/排行（先把单群一局做扎实）。

## 2. 总体架构

```
                     ┌─────────────────────────────────────────────┐
  群友消息 ─────────►│ Orchestrator 正常运行（现有链路不变）        │
                     │  · 若有进行中的局，把该局状态摘要注入提示词   │
                     └───────────────┬─────────────────────────────┘
                                     │ 模型可调用
                                     ▼
                     ┌─────────────────────────────────────────────┐
                     │ group_game 工具（薄层）                      │
                     │  action: start/join/status/stop/next        │
                     └───────────────┬─────────────────────────────┘
                                     ▼
                     ┌─────────────────────────────────────────────┐
                     │ GroupGameManager（新，src/features/）        │
                     │  · 每群至多一局；注册表：gameId → 插件       │
                     │  · 生命周期：idle→recruiting→running→ended  │
                     │  · 持久化 data/games.json（原子写）          │
                     │  · 回合超时 → 回调 orchestrator 唤醒主持     │
                     └───────────────┬─────────────────────────────┘
                                     ▼
                     ┌─────────────────────────────────────────────┐
                     │ 游戏插件（每个游戏一个文件）                 │
                     │  meta / create / onMessage / onTick /       │
                     │  serialize / summaryForModel / effects      │
                     └─────────────────────────────────────────────┘
```

### 2.1 关键分层：真相与话术分离

| 层 | 掌握什么 | 例子（谁是卧底） |
|---|---|---|
| 状态机（代码） | 谁是什么词、投票计数、存活/淘汰、计时 | 词对（"豆浆/牛奶"）、票数表 |
| 模型（主持） | 只拿到"该说什么"的摘要与指令 | "第 2 轮发言，请按顺序点人：3 号该发言了" |

- 状态机生成**给模型看的摘要**（`summaryForModel(state, forWhom)`），只含允许公开/该角色可见的信息。
- 私密信息（身份、词）**只通过私聊**发给玩家，绝不进群聊上下文与模型上下文。
- 判定（谁出局、输赢）由状态机算，模型不判胜负——避免模型算错和被"嘴遁"。

### 2.2 与现有运行链路的结合方式

1. **进行中的局会影响每次普通运行**：orchestrator 在构建提示词时，如果该群有活动中的局，
   注入一段"【进行中的游戏】<公开状态摘要> + 主持人指令"（几百字符，走省 Token 上限）。
2. **模型通过 `group_game` 工具操作局**：`start`（发起报名）、`stop`（中止）、`status`（查询）。
   参与者动作（发言、投票）**不通过工具**——直接从群消息里由插件解析（普通发言就是参与）。
3. **回合超时自驱**：插件声明"本回合截止时刻"；Manager 用一个 30 秒 ticker 检查，到点把
   `kind:'game'` 的唤醒排给 orchestrator（复用 `scheduleInitiativeWake`），模型醒来看到
   "轮次超时，请宣布结果/推进"的指令后照常发言。超时/宕机期间未处理的输入在恢复后由插件
   按时间戳补齐（`store.recent` 带时间）。
4. **重启恢复**：`data/games.json` 保存进行中的局；启动时 Manager 载入并把"快照摘要"写回。
   超过 `maxDurationMin`（默认 60 分钟）的局在启动时自动判和/结束。

## 3. 插件接口（每个游戏一个模块）

```js
// src/features/games/<game>.js
export const meta = {
  id: 'undercover',            // 稳定 id（配置/UI 用）
  name: '谁是卧底',
  minPlayers: 4, maxPlayers: 10,
  needsPrivate: true,           // 需要私聊发身份（风控相关，配置里要显式允许）
  roundSeconds: 90,             // 单回合超时
  maxDurationMin: 45
};

export function create({ players, rng, now }) {           // 报名结束 → 开局
  return { phase: 'speak', round: 1, order: [...players], cursor: 0, tickets: {}, ... };
}

// 群消息进入：只处理与本局相关的（投票格式、关键词），返回 effect 数组
export function onMessage(state, msg, { now, rng }) {
  // return { state, effects: [ {type:'public', text}, {type:'private', userId, text},
  //                            {type:'wake', delayMs}, {type:'end', result} ] }
}

export function onTick(state, { now }) { /* 超时推进/淘汰/结算，同上返回 */ }

// 给模型的公开摘要（用于提示词注入）与该说的主持词骨架（模型会润色成人设口吻）
export function summaryForModel(state) { /* 纯文本，不含隐藏信息 */ }
export function hostBrief(state) { /* 模型本轮要做的事，1-3 句 */ }

export function serialize(state) { return state; }       // JSON 安全
export function deserialize(raw) { return raw; }
```

**插件不直接发消息**——只产出 `effects`，由 Manager 统一交给 `sender` 发送（含限频、引用、
私聊通道与失败降级）。这样发送路径只有一处，风控与限流策略集中可控。

### 3.1 状态机骨架（Manager 负责，插件不重复实现）

```
idle ──start──► recruiting ──(人数够/报名超时)──► running ──(插件判胜/超时/stop)──► ended
                    │                              │
                    └──(报名不足)──► ended         └──(管理员 stop / 时长上限)──► ended
```

- `recruiting`：默认 120 秒；"报名"= 群友在窗口内发任意非指令消息，或 `group_game join`。
  **现状（2026-09-29）：未实现**——M1 落地时改成"名单由模型/活跃成员直接给"（`players` 支持
  群名片），够人数就开局，`recruiting` 这一档被跳过。对人数刚性的游戏（狼人杀正好 6/9 人）
  它才是刚需：建议随狼人杀一起补（缺 1~2 人时挂"报名中，还差 N 人"，而不是直接报错）。
- `running`：每回合由插件给出 `deadlineAt`；Manager ticker 到点派唤醒。
- `ended`：输出结算文本（公开），清状态；可选把"本局战绩"写进人物记忆（默认关）。

## 4. 候选游戏矩阵与推荐顺序

| 游戏 | 需要状态 | 需要私聊 | 风控面 | 实现量 | 建议 |
|---|---|---|---|---|---|
| **数字炸弹**（区间猜数，命中者输） | 极小 | 否 | 无 | 0.5 天 | **M1 首作**：先验证框架，全公开信息 |
| **谁是卧底** | 中（词/票/轮） | 是（发词） | 中（私聊） | 1.5 天 | **M1 主力**：框架的第一个完整展示 |
| 猜词接龙赛（你说我猜/词库接龙计分） | 小（计分） | 否 | 无 | 0.5 天 | M2 |
| 狼人杀（简化 6 人：狼/预/守/民） | 大（夜/昼、技能、遗言） | 是（发身份） | 高（私聊+时长） | 3 天+ | M3，方案细化见 §4.2 |
| UNO/牌类 | 中（手牌） | 是（手牌） | 中 | 2 天 | 观望（娱乐性强但状态多） |
| 真心话大冒险（抽签+点到） | 无 | 否 | 低 | 0（L0 提示词即覆盖） | 已随 L0 提供 |

**推荐落地顺序**：数字炸弹（0.5 天，跑通框架）→ 谁是卧底（1.5 天，验证私聊与回合）→ 控制台开关页
→ 再看社区呼声决定狼人杀/牌类。

### 4.1 谁是卧底（首发的完整状态机要点）

1. `create`：从词库抽一对相近词（"豆浆/牛奶"），随机发身份：1 个卧底、其余平民；
   私聊每位玩家"你的词：X，别直接说出来"。抽词用 `rng`（可注入，测试可复现）。
2. 发言轮：按报名顺序，每人一条描述（模型只提示"轮到 3 号"）。状态机不做语义判断，
   玩家描述是人话即可（若插件要求"必须与词相关"则用关键词免责——不校验，避免误伤）。
3. 投票轮：群友发"投 3"或在消息里 @ 某人；插件解析出票，票高者出局（平票→重投一次，
   再平→本轮不出局）。投票消息本身也由模型看见，但**判定以插件解析结果为准**。
4. 胜负：卧底出局=平民胜；存活人数 ≤2 且卧底在场=卧底胜；轮次上限 5。
5. 主持话术由模型润色（`hostBrief` 给骨架）：不暴露身份、不评价词、不催票超 2 次。

### 4.2 狼人杀（M3，2026-09-29 细化；与谁是卧底的两个本质差异写在这里）

谁是卧底的私聊只有"开局发词"一种（发完就完），狼人杀的私聊是**贯穿全程的行动通道**——
这引出两件方案正文没覆盖、必须先解决的事（入站私聊通道、私聊白名单豁免），见下。

**角色与规模**：6 人 = 2 狼 / 1 预言家 / 1 守卫 / 2 民；8 人 = 2 狼 / 1 预 / 1 守 / 4 民；
9 人 = 3 狼 / 1 预 / 1 守 / 4 民。不做警长、不做女巫双药（先跑通再谈）。发身份时同阵营
互相可见（狼人 Deal 里写明队友）。

**阶段机（state.phase）**：`deal` → `night`（守→刀→查，按角色顺序私聊收集行动）→ `dawn`
（公布死讯或平安夜）→ `day`（发言轮，复用卧底的 cursor 制）→ `vote`（"投 3"，复用 tally）
→ 出局遗言（出局者在群里公开说，引擎不拦）→ 胜负判定 → 回 `night`。轮次上限 6，用尽判平局
（公布全部身份）。

**夜晚行动——框架要新增的能力（① 入站私聊通道）**：
- 现状：tick 只扫**群消息**。夜晚行动必须走私聊（玩家私聊机器人"刀 3 号"/"查 2 号"），
  消息落在 `private:uid` 会话，现在的引擎根本看不到。
- 扩展：Manager 对 running 且 needsPrivate 的局，tick 额外扫**每位在册玩家**的私聊会话
  （`store.recent(private:uid, { readOnly, afterId: 每人水位 })`），把私聊消息带
  `{ kind: 'private' }` 喂给插件（onMessage 加来源标记或单独 `onPrivateMessage` 钩子）。
- 水位存进 state（持久化）：重启恢复后不重放旧消息、不重发夜提示。
- 语义：**重复提交 = 覆盖提交**（夜里允许改主意）；每人行动窗口 90 秒，超时 = 本夜空过
  （狼队各自私下提交，多数一致生效，平票 rng 随机；守卫可守自己、不能连续两晚守同一人）；
  守卫目标 = 狼刀目标 → 平安夜；预言家查一个人，结果由引擎**私聊直发本人**。

**行动确认不由模型做（省调用 + 零泄密面）**：
- 引擎收到行动立即私聊回执（"✔ 已收到你的行动，天亮公布"），并对该会话 `drainUnread`——
  夜晚的私聊消息**不再唤醒模型**。否则每次行动都会在私聊里触发一次模型运行，而那个上下文
  里没有游戏信息，模型只会胡乱接话。
- 白天玩家的私聊照常聊天（不受影响）；`summaryForModel` 需要一个**角色无关**的私聊版本
  （"这场游戏的行动收集中/你已出局"），身份与夜晚行动永不进模型上下文（§2.1 不变量）。

**② 私聊白名单豁免（策略决策点，先定再做）**：
- 实测（谁是卧底上线当天）：私聊白名单把非 `allow.private` 成员的词**全部拦掉**（9 人局 8 人
  收不到）。谁是卧底只有"发词"一种私聊尚且如此；狼人杀人均 3~6 条 DM，没有豁免就只有
  "全员都在白名单里"才玩得起来。
- 方案：**游戏范围豁免**——引擎产出的 private effect 发给**在册玩家**时不受 `allow.private`
  限制（报名 = 同意接收），仅限本局进行中、失败不重试、内容全部是引擎文本
  （**模型不产出任何私聊内容**，模型的 `send_message` 工具仍受白名单硬门）。
  实现为 sender 专用方法 `sendPrivateGame(userId, text)`：跳过 allow.private 检查，
  保留 time-gate / 禁言 / 限频。
- 风控账：6 人局 DM 总量 ≈ 发身份 6 + 每夜提示 3~4 × 夜数 3~5 + 回执若干 ≈ 20~30 条/局，
  全部发给了主动报名的玩家、可随时 stop，`dailyLimitPerChat` 兜底。对照好友退役的教训：
  不批量（只发在册者）、不重试、内容固定——量级可控。

**主持模型**：黎明/白天照常唤醒润色（wake effect，`hostBrief` 按阶段给骨架：夜里不催具体
行动内容，白天也别顺着遗言里的身份暗示往下推）；`summaryForModel` 公开版只含存活名单、
天数、公开死讯——与卧底同口径。

**胜负**：狼全灭 = 好人胜；狼数 ≥ 好人数 = 狼胜。结算公布全部身份与每晚实际刀/守/查
（受 `revealWords` 开关控制，默认开）。

**实现量重估**：①入站私聊通道 + ②游戏豁免 ≈ 1 天（框架层，UNO/牌类同吃这个红利）；
狼人杀插件 ≈ 2 天；测试 ≈ 1 天（game-drive 加"假私聊"整局驱动 + 夜晚中途重启恢复 +
超时空刀 + 越权路径）。合计 **3~4 天**。

## 5. 配置、开关与安全

```jsonc
{
  "groupGame": {
    "enabled": false,            // 实验特性，默认关（遵守 EXPERIMENTAL_FEATURE_STANDARD）
    "chats": ["group:123"],      // 白名单：只在这些群可开局（空=不开局）
    "maxConcurrentPerChat": 1,   // 每群同时一局（硬约束）
    "allowPrivateInvite": false, // 是否允许私聊发身份（默认关；开启前先在控制台确认）
    "dailyLimitPerChat": 5,      // 每群每天最多开局数（防沉迷/防滥用）
    "maxDurationMin": 60         // 单局时长上限，到点自动结算
  }
}
```

- **风控**：私聊是唯一的"对外主动"行为——默认关闭；开启后只对**报名者**发、失败不重试。
  "每人每局 1 条"只对谁是卧底（发词）成立；狼人杀这类需要全程私聊行动的游戏按 §4.2 的
  游戏范围豁免走（只发在册玩家、只发引擎文本、局内有效）。参照好友退役一节的教训：
  绝不批量、绝不对非报名者发、绝不重试。
- **防卡局**：回合超时→唤醒主持；连续 3 次无人响应→自动结束；管理员 `stop` 随时可用。
- **实验特性流程**：走 `EXPERIMENTAL_FEATURE_STANDARD`（开关、默认关、观察后转正），
  控制台放"实验"页，转正标准 = 有真实群连续使用 2 周无卡局。
- **成本**：局内每轮只注入摘要（≤600 字符），回合唤醒走省 Token 上限；一局预算估算
  ≈ 20~40 次模型调用（远小于同时间的自由聊天）。

## 6. 实施步骤（含验收）

**M1（框架，2 天）**
1. `src/features/group-game.js`：Manager（生命周期、ticker、持久化、effects 派发）。
2. `group_game` 工具（start/stop/status）+ ctx 接线 + 提示词注入"进行中的游戏"段。
3. 插件：`games/number-bomb.js` → 端到端脚本测试（假时钟 + 假玩家驱动整局）。
4. 插件：`games/undercover.js` + 私聊发送通道（`sender.sendPrivate` 已有 → 走 `sendText('private')`）。
5. 测试：`test/group-game.test.mjs`（框架状态机 + 两个插件的正常/超时/中止/恢复路径，用注入 rng 与假时钟）。

**M2（体验与可运维，1.5 天）**
6. 控制台实验页开关 + 局内状态可视化（正在进行的局、强制结束）。
7. 战绩写记忆（可选）、每日局数上限、`daily-moments` 式调度统计日志。

**M3（更多游戏，按社区呼声）**
8. 狼人杀简化版 / 牌类；每个新游戏只写插件（框架不变）。

**验收标准（硬）**：① 一局完整跑通且中途重启能从 games.json 恢复；② 超时/无人响应/管理员中止
三条路径都有用例；③ 私聊只在 `allowPrivateInvite=true` 且对方报名后发送，失败不回退到群聊泄密；
④ 与普通聊天互不干扰（有局时聊天照常，提示词只多一段摘要）；
⑤ 狼人杀追加：夜晚行动只认在册玩家私聊、夜晚中途重启不重发提示、查验结果只达本人、
行动确认不经模型（drainUnread 生效）。

## 7. 风险清单

| 风险 | 缓解 |
|---|---|
| 私聊触发风控（历史上加好友实验的教训） | 默认关、只发报名者、每人 1 条、绝不重试（狼人杀的 DM 量级远超"每人 1 条"，走 §4.2 的游戏范围豁免：只发在册玩家、只发引擎文本、局内有效、dailyLimit 兜底） |
| 卡局（有人掉线/群冷掉） | 回合超时唤醒 + 连续无响应自动结束 + 时长上限 |
| 模型说漏身份 | 身份只走私聊，公开摘要不含隐藏信息（结构上不可能说漏） |
| 群友不按格式投票（"我投那个说豆浆的"） | 插件解析宽松匹配（序号/昵称/@），歧义时由模型主持澄清（话术层），判定仍由插件 |
| 状态膨胀 | 只留当前局 + 最近 1 局的结算摘要；games.json 原子写 |
| 与实验特性规范冲突 | 走标准流程：默认关、控制台开关、观察转正 |
| 夜晚行动依赖玩家私聊活跃度（AFK 不交行动） | 每个行动 90 秒窗口，超时空过（空刀/不守/不查）；连续整夜无人行动 → 自动结束 |
