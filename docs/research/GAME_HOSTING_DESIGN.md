# 多人游戏状态机（群游戏主持）设计与实施方案

> 状态：M1 已实现（2026-09-28，数字炸弹 + 谁是卧底）；**M3 狼人杀也已实现**（2026-09-29，
> 含两个框架扩展：入站私聊通道与游戏期间私聊豁免开关）。代码在 `src/features/group-game.js`
> 与 `src/features/games/`，开关与配置项见 `CONFIG-EXAMPLES.md` 的 `groupGame` 一节。
> 读者：维护者。
> 目标：让机器人在群里**主持需要状态与回合的多人游戏**，
> 把"只有聊天"的观感变成"群里有个会陪你玩的家伙"。
>
> 前置事实：本仓库已有 `dice/random`、`get_group_member_list` 两个小工具与玩法提示词（L0，
> 无状态轻游戏：成语接龙、猜数字、20 问、抽签——模型自己当主持人即可），本方案是它上面的 L1：
> **需要"隐藏信息、轮次、超时、计分"的游戏**（谁是卧底、狼人杀、数字炸弹、猜词比赛等）。

---

## 1. 设计目标与非目标

**目标**

1. 群友自然发起（"来个谁是卧底"）→ 机器人主持完整一局：报名、发身份、轮次推进、判定、结算。
2. 状态机管**规则与真相**，模型管**主持话术与自由判断**——模型不接触它不该知道的信息（例如谁是卧底里
   谁是什么词），真相不进入模型上下文就能天然防"说漏嘴"。
3. 一局可跨多次运行（群消息是逐批唤醒的），也能**跨重启恢复**。
4. 全程可中止、可超时、可被管理员关闭；对群友零学习成本（就用 @ 和普通发言参与）。
5. 复用现有基建：唤醒（`scheduleInitiativeWake`）、发送（`sender`）、消息库（`store.recent`）、
   活跃时段（`time-gate`）、省 Token 上限（`token-saver`）、实验特性规范（`stable-feature-policy`）。

**非目标（本方案不做）**

- 不做**赌博/竞猜下注**类（合规与群规风险）。
- 不做需要账号权限或批量对外动作的玩法（好友申请已退役的教训）。
- 不做实时对局（音游/棋类需要毫秒级同步；QQ 群消息本身是秒级异步）。
- 不做跨群联赛/排行（先把单群一局做扎实）。

## 2. 总体架构

```
                     ┌─────────────────────────────────────────────┐
  群友消息 ─────────►│ Orchestrator 正常运行（现有链路不变）        │
                     │  · 若有进行中的局，把该局状态摘要注入提示词   │
                     └───────────────┬─────────────────────────────┘
                                     │ 模型可调用
                                     ▼
                     ┌─────────────────────────────────────────────┐
                     │ group_game 工具（薄层）                      │
                     │  action: start/join/status/stop/next        │
                     └───────────────┬─────────────────────────────┘
                                     ▼
                     ┌─────────────────────────────────────────────┐
                     │ GroupGameManager（新，src/features/）        │
                     │  · 每群至多一局；注册表：gameId → 插件       │
                     │  · 生命周期：idle→recruiting→running→ended  │
                     │  · 持久化 data/games.json（原子写）          │
                     │  · 回合超时 → 回调 orchestrator 唤醒主持     │
                     └───────────────┬─────────────────────────────┘
                                     ▼
                     ┌─────────────────────────────────────────────┐
                     │ 游戏插件（每个游戏一个文件）                 │
                     │  meta / create / onMessage / onTick /       │
                     │  state(JSON 安全) / summaryForModel / effects│
                     └─────────────────────────────────────────────┘
```

### 2.1 关键分层：真相与话术分离

| 层 | 掌握什么 | 例子（谁是卧底） |
|---|---|---|
| 状态机（代码） | 谁是什么词、投票计数、存活/淘汰、计时 | 词对（"豆浆/牛奶"）、票数表 |
| 模型（主持） | 只拿到"该说什么"的摘要与指令 | "第 2 轮发言，请按顺序点人：3 号该发言了" |

- 状态机生成**给模型看的摘要**（`summaryForModel(state, forWhom)`），只含允许公开/该角色可见的信息。
- 私密信息（身份、词）**只通过私聊**发给玩家，绝不进群聊上下文与模型上下文。
- 判定（谁出局、输赢）由状态机算，模型不判胜负——避免模型算错和被"嘴遁"。

### 2.2 与现有运行链路的结合方式

1. **进行中的局会影响每次普通运行**：orchestrator 在构建提示词时，如果该群有活动中的局，
   注入一段"【进行中的游戏】<公开状态摘要> + 主持人指令"（几百字符，走省 Token 上限）。
2. **模型通过 `group_game` 工具操作局**：`start`（发起报名）、`stop`（中止）、`status`（查询）。
   参与者动作（发言、投票）**不通过工具**——直接从群消息里由插件解析（普通发言就是参与）。
3. **回合超时自驱**：插件声明"本回合截止时刻"；Manager 用一个 30 秒 ticker 检查，到点把
   `kind:'game'` 的唤醒排给 orchestrator（复用 `scheduleInitiativeWake`），模型醒来看到
   "轮次超时，请宣布结果/推进"的指令后照常发言。超时/宕机期间未处理的输入在恢复后由插件
   按时间戳补齐（`store.recent` 带时间）。
4. **重启恢复**：`data/games.json` 保存进行中的局；启动时 Manager 载入并把"快照摘要"写回。
   超过 `maxDurationMin`（默认 60 分钟）的局在启动时自动判和/结束。

## 3. 插件接口（每个游戏一个模块）

```js
// src/features/games/<game>.js
export const meta = {
  id: 'undercover',            // 稳定 id（配置/UI 用）
  name: '谁是卧底',
  minPlayers: 4, maxPlayers: 10,
  needsPrivate: true,           // 需要私聊发身份（风控相关，配置里要显式允许）
  roundSeconds: 90,             // 单回合超时
  maxDurationMin: 45
};

export function create({ players, rng, now, reveal, discussSeconds }) {   // 报名结束 → 开局
  return { phase: 'speak', round: 1, order: [...players], cursor: 0, tickets: {}, ... };
}

// 开局要发的消息（身份私聊 + 夜行动提示）：只在发牌这一刻调一次
export function openingEffects(state) {
  // return [ {type:'public', text}, {type:'private', userId, text} ]
}

// 群消息进入：只处理与本局相关的（投票格式、关键词），返回 effect 数组
export function onMessage(state, msg, { now, rng }) {
  // return { state, effects: [ {type:'public', text}, {type:'private', userId, text},
  //                            {type:'wake', delayMs}, {type:'end', result} ] }
}

// 私聊消息进入（夜里提交行动）：只有 needsPrivate 的局会用；返回同上，另可带 consume:true
// 表示"插件已接管这条消息，但不需要回消息"（比如同一目标的重复提交）
export function onPrivateMessage(state, msg, { now, rng }) { /* ... */ }

export function onTick(state, { now, deadline, rng }) { /* 超时推进/淘汰/结算，同上返回 */ }

// 给模型的公开摘要（用于提示词注入）与该说的主持词骨架（模型会润色成人设口吻）
export function summaryForModel(state) { /* 纯文本，不含隐藏信息 */ }
export function hostBrief(state) { /* 模型本轮要做的事，1-3 句 */ }

// 没有 serialize/deserialize 钩子：state 必须是 JSON 安全的对象，Manager 直接整对象落盘
// （games.json 整存整取，含每夜行动水位与游戏自己的字段）。
```

> 没有单独的 `quitPlayer` 导出：玩家说「不玩了/退出」时，插件在自己的 `onMessage`（群消息）
> 与 `onPrivateMessage`（私聊）里用 `QUIT_RE` 识别，内部函数处理（移出名单、作废其票、
> 立刻重算胜负），效果通过 `effects` 返回。
>
> Manager 侧对私聊还有两个入口：`consumePrivateAction(chatKey, stored)`（实时链路，ingest 一落库就调）
> 与 tick 里的兜底扫描（补"重启期间/引擎当时没在跑"漏掉的行动），两者共用同一插件方法。

**插件不直接发消息**——只产出 `effects`，由 Manager 统一交给 `sender` 发送（含限频、引用、
私聊通道与失败降级）。这样发送路径只有一处，风控与限流策略集中可控。

### 3.1 状态机骨架（Manager 负责，插件不重复实现）

```
idle ──start──► recruiting ──(人数够/报名超时)──► running ──(插件判胜/超时/stop)──► ended
                    │                              │
                    └──(报名不足)──► ended         └──(管理员 stop / 时长上限)──► ended
```

- `recruiting`：**已实现（2026-09-29）**，默认 45 秒（`groupGame.recruitSeconds`，0 = 关闭）。
  "报名" = 群里发一句「我玩/报名/加我/算我/+1」这类**明确信号**（`JOIN_RE`，不是任意消息——
  避免把插句话的围观者拉进局）；够 `minPlayers` 立刻发牌，到点不够就取消并公告。
  报名阶段**不发任何私聊**（不再有"没报名却收到身份"）。模型显式给 `players`（群名片/QQ 号）时跳过报名。
- `running`：每回合由插件给出 `deadlineAt`；Manager ticker 到点派唤醒。
- `ended`：输出结算文本（公开），清状态；可选把"本局战绩"写进人物记忆（默认关）。

## 4. 候选游戏矩阵与推荐顺序

| 游戏 | 需要状态 | 需要私聊 | 风控面 | 实现量 | 建议 |
|---|---|---|---|---|---|
| **数字炸弹**（区间猜数，命中者输） | 极小 | 否 | 无 | 0.5 天 | **M1 首作**：先验证框架，全公开信息 |
| **谁是卧底** | 中（词/票/轮） | 是（发词） | 中（私聊） | 1.5 天 | **M1 主力**：框架的第一个完整展示 |
| 猜词接龙赛（你说我猜/词库接龙计分） | 小（计分） | 否 | 无 | 0.5 天 | M2 |
| 狼人杀（简化 6~9 人：狼/预/女巫/守/民） | 大（夜/昼、技能、遗言） | 是（发身份+夜行动） | 高（私聊+时长） | 3 天+ | M3，方案细化见 §4.2 |
| UNO/牌类 | 中（手牌） | 是（手牌） | 中 | 2 天 | 观望（娱乐性强但状态多） |
| 真心话大冒险（抽签+点到） | 无 | 否 | 低 | 0（L0 提示词即覆盖） | 已随 L0 提供 |

**推荐落地顺序**：数字炸弹（0.5 天，跑通框架）→ 谁是卧底（1.5 天，验证私聊与回合）→ 控制台开关页
→ 再看社区呼声决定狼人杀/牌类。

### 4.1 谁是卧底（首发的完整状态机要点）

1. `create`：从词库抽一对相近词（"豆浆/牛奶"），随机发身份：1 个卧底、其余平民；
   私聊每位玩家"你的词：X，别直接说出来"。抽词用 `rng`（可注入，测试可复现）。
2. 发言轮：**谁想说就说**（实现已改，2026-09-29）——不点名、不催"轮到谁"，谁发过一句就算发过言
   （`spoken` 集合去重）；全员说过 / 固定讨论时长到 / 过半人说「投吧」→ 进投票。
   状态机不做语义判断，玩家描述是人话即可。
3. 投票轮：群友发"投 3"或在消息里 @ 某人；插件解析出票，票高者出局（平票→重投一次，
   再平→本轮不出局）。投票消息本身也由模型看见，但**判定以插件解析结果为准**。
4. 胜负：卧底出局=平民胜；存活人数 ≤2 且卧底在场=卧底胜；**轮次上限 4**（实现值）。
   投票平票**直接进下一轮**（不是重投）。
5. 主持话术由模型润色（`hostBrief` 给骨架）：不暴露身份、不评价词、不催票超 2 次。

### 4.2 狼人杀（**已实现** 2026-09-29；与谁是卧底的两个本质差异写在这里）

> 落地情况：`src/features/games/werewolf.js`（插件）+ 管理器两个扩展
> （`consumePrivateAction` 入口接管 / `#collectPrivateActions` 兜底扫描 / `privateSeen` 水位 /
> gameScoped 私聊豁免）。控制台可勾选「狼人杀」并开关「游戏期间私聊豁免」。
> 测试：`test/werewolf.test.mjs`、`test/undercover.test.mjs`（规则与边界回归，含女巫四例 + 刀口锁定）、
> `test/group-game.test.mjs`（私聊通道 + 豁免 + 报名）、
> `test/local/game-drive.mjs`（7 人整局驱动，含挡刀/解药/毒药/查验/投票/胜负）、
> `test/local/game-sim.mjs`（虚拟群：报名→夜行动→天亮→白天讨论→投票→重开一局，含"救人生效→平安夜"与"救改毒"）。
> 仍待社区验证的点：真人群里的节奏与 AFK 比例、夜行动窗口 90 秒是否合适。

谁是卧底的私聊只有"开局发词"一种（发完就完），狼人杀的私聊是**贯穿全程的行动通道**——
这引出两件方案正文没覆盖、必须先解决的事（入站私聊通道、私聊白名单豁免），见下。

**角色与规模**：6 人 = 2 狼 / 1 预言家 / 1 女巫 / 2 民（6 人局无守卫）；7 人 = 加 1 守卫；
8 人 = 2 狼 / 1 预 / 1 女巫 / 1 守 / 3 民；9 人 = 3 狼 / 1 预 / 1 女巫 / 1 守 / 3 民。
不做警长。发身份时同阵营互相可见（狼人 Deal 里写明队友）。

**女巫（2026-09-29 加入）**：两瓶药各一次——**解药**救今晚被刀的人、**毒药**毒一个人。
规则四条：①**一晚最多用一瓶**（先回「救」再回「毒 3」= 后者覆盖，最终只算一瓶）；
②**不能自救**（狼刀落在女巫自己身上时，提示明确写"不能自救"，只给"不救/下毒"两个选项）；
③**同守同救必死**（守卫守了同一个人、女巫又用解药 → 仍出局，防"双保险"让狼刀失效；
只守不救 / 只救不守照常活）；④**毒药独立致命**（毒的目标与狼刀无关，可以一晚双死）。
顺序上，女巫**在狼刀定下来之后才被问**（提示里直接告诉她"今晚被刀的是 X 号"），
因此狼提交刀口后、女巫收到提示后再改刀会被拒绝（`刀口已经定下（女巫知道是谁了）`）——
否则女巫按旧刀口做的决定会失效。药水在**夜晚结算时扣**（用了就是用了，即使目标因同守同救仍出局）。
女巫死了/出局后不再被问、也不能用药；白天群里说的「毒 X」不算行动（只认私聊）。

**阶段机（state.phase）**：`night`（按守→刀→**刀定下后问女巫**→查 私聊收行动）→ 天亮公布死讯/平安夜（同一次结算里
出 `day` 的公告）→ `day`（谁想说就说 + 固定讨论时长 + 过半「投吧」）→ `vote`（"投 3"，tally）
→ 胜负判定 → 回 `night`。出局者的遗言在群里公开说，引擎不拦。夜数上限 6，用尽判平局。
（没有单独的 `dawn`/`deal` 阶段；发牌即 `night`。"复用时序 cursor 制"已废弃——cursor 现在还留着，
只用于展示"第几号人"。）

**夜晚行动——框架要新增的能力（① 入站私聊通道）**：
- 现状：tick 只扫**群消息**。夜晚行动必须走私聊（玩家私聊机器人"刀 3 号"/"查 2 号"），
  消息落在 `private:uid` 会话，现在的引擎根本看不到。
- 扩展：Manager 对 running 且 needsPrivate 的局，tick 额外扫**每位在册玩家**的私聊会话
  （`store.recent(private:uid, { readOnly, afterId: 每人水位 })`），把私聊消息带
  `{ kind: 'private' }` 喂给插件（onMessage 加来源标记或单独 `onPrivateMessage` 钩子）。
- 水位存进 state（持久化）：重启恢复后不重放旧消息、不重发夜提示。
- 语义：**重复提交 = 覆盖提交**（夜里允许改主意）；每人行动窗口 90 秒，超时 = 本夜空过
  （狼队各自私下提交，多数一致生效，平票 rng 随机；守卫可守自己、不能连续两晚守同一人）；
  守卫目标 = 狼刀目标（且女巫没用解药）→ 平安夜；预言家查一个人，结果由引擎**私聊直发本人**；
  女巫在刀口定下后收到"被刀的是 X"，回「救 / 不救 / 毒 3」（细则见上"女巫"段）。

**行动确认不由模型做（省调用 + 零泄密面）**：
- 引擎收到行动立即私聊回执（"✔ 已收到你的行动，天亮公布"），并对该会话 `drainUnread`——
  夜晚的私聊消息**不再唤醒模型**。否则每次行动都会在私聊里触发一次模型运行，而那个上下文
  里没有游戏信息，模型只会胡乱接话。
- 白天玩家的私聊照常聊天（不受影响）；`summaryForModel` 需要一个**角色无关**的私聊版本
  （"这场游戏的行动收集中/你已出局"），身份与夜晚行动永不进模型上下文（§2.1 不变量）。

**② 私聊白名单豁免（策略决策点，先定再做）**：
- 实测（谁是卧底上线当天）：私聊白名单把非 `allow.private` 成员的词**全部拦掉**（9 人局 8 人
  收不到）。谁是卧底只有"发词"一种私聊尚且如此；狼人杀人均 3~6 条 DM，没有豁免就只有
  "全员都在白名单里"才玩得起来。
- 方案：**游戏范围豁免**——引擎产出的 private effect 发给**在册玩家**时不受 `allow.private`
  限制（报名 = 同意接收），仅限本局进行中、失败不重试、内容全部是引擎文本
  （**模型不产出任何私聊内容**，模型的 `send_message` 工具仍受白名单硬门）。
  实现形态是 `sender.sendTextBatch('private:uid', [...], { gameScoped: true })`（`access.assertCanSend`
  识别这个标记：放宽 allow.private、deny 仍优先、活跃时段照旧），没有单独的 sendPrivateGame 方法。
- 风控账：6 人局 DM 总量 ≈ 发身份 6 + 每夜提示 3~4 × 夜数 3~5 + 回执若干 ≈ 20~30 条/局，
  全部发给了主动报名的玩家、可随时 stop，`dailyLimitPerChat` 兜底。对照好友退役的教训：
  不批量（只发在册者）、不重试、内容固定——量级可控。

**主持模型**：黎明/白天照常唤醒润色（wake effect，`hostBrief` 按阶段给骨架：夜里不催具体
行动内容，白天也别顺着遗言里的身份暗示往下推）；`summaryForModel` 公开版只含存活名单、
天数、公开死讯——与卧底同口径。

**胜负**：狼全灭 = 好人胜；狼数 ≥ 好人数 = 狼胜。结算公布全部身份与每晚实际刀/守/查/救/毒
（受 `revealWords` 开关控制，默认开）。公开摘要里的"昨日死讯"取自**实际出局名单**（狼刀 ∩ 守卫/解药
判定 + 毒药去重后仍在场的人），所以毒杀会报出来、被刀的人在结算前退出则报平安夜。

**实现量重估**：①入站私聊通道 + ②游戏豁免 ≈ 1 天（框架层，UNO/牌类同吃这个红利）；
狼人杀插件 ≈ 2 天；测试 ≈ 1 天（game-drive 加"假私聊"整局驱动 + 夜晚中途重启恢复 +
超时空刀 + 越权路径）。合计 **3~4 天**。

### 4.3 群里的真实情况：边界决策表（2026-09-29 与实现同步）

真群不是模拟环境——下面这些场景都在代码里有明确行为，改动前先看这张表。

| 场景 | 行为 | 位置 |
|---|---|---|
| **没参加这局的人在群里发言/投票** | 角色类游戏（卧底/狼人杀）**只认在册玩家**：发言不进发言轮、`投 X` 不计票、"刀/查/守"一律忽略；模型照常跟他聊（`hostBrief` 叮嘱别把他的话当有效动作） | `undercover.onMessage` / `werewolf.onMessage` 开头的在册判定 |
| **谁才算"参加"了这局** | **报名制**（默认 45 秒）：需要私聊的游戏先挂报名公告，想玩的回「我玩/报名」才进名单、才收到私聊；够人数立刻发牌，到点不够就取消。`recruitSeconds: 0` 关闭报名（回到"按最近发言者发牌"）；模型显式给名单也跳过报名 | `#collectRecruiting` + `JOIN_RE` + `#cfg().recruitSeconds` |
| **没参加这局的人猜数字（数字炸弹）** | **照常算数**：数字炸弹是公共游戏（开局文案就写"直接发你猜的数字"），谁都能猜、猜中照样结算——刻意不做在册门槛，否则新来的群友猜了没反应会莫名 | `number-bomb.onMessage`（无在册判定） |
| **没参加的人私聊机器人** | 不进游戏引擎（`consumePrivateAction` 返回 false），走普通私聊 | `group-game.#playerGameOfPrivate` |
| **参加者在群里/私聊说"不玩了/退出/观战/弃权"** | 移出本局：身份不公布、群里播报"👋 X 退出了本局"、本人收到确认；发言轮里该他直接跳过、已投的票作废；**立刻重算胜负**（狼/卧底退光就直接分胜负）；夜里退出的正好是待行动者时，行动齐了马上结算 | `werewolf.onMessage`/`onPrivateMessage` 里的 `QUIT_RE`（插件内部 `quitPlayer()`，群消息与私聊都认；不是导出接口） |
| **有人反复私聊刷行动** | 同一目标的重复提交 = **静默消耗**（第一条回过执了）；每人每夜最多 4 条回执，超出后静默（**行动照收**，最后一次生效）；查验结果不受配额（玩法信息必须送达）；出局者反复私聊同样受配额 | `werewolf.onPrivateMessage` 的 `ackCount` / `MAX_ACKS_PER_NIGHT` |
| **夜里有人私聊闲聊（不是行动）** | 非行动消息：村民/看不懂的分支会给一句回执并在配额内被消耗；白天私聊完全走普通聊天（引擎不碰） | 同上（`phase !== 'night'` 返回空 effects） |
| **白天聊天不按顺序（真人群必然乱序）** | **谁想说就说**：不点名、不催"轮到谁"、不为"没轮到"刷提示；谁发过一句就算发过言（`spoken` 集合去重）；**边说边投**也认：「投 3」直接记成他的票并在切到投票阶段时保留 | `werewolf.onMessage` / `undercover.onMessage` 的发言分支 + `voteTargetOf` |
| **白天聊多久、什么时候投票** | 三个出口：①**固定讨论时长**（`groupGame.discussSeconds`，默认 120 秒）到点自动进投票；②**超过半数存活玩家**说「投吧/直接投」（不带目标）立刻开投；③所有人都发过言也立刻开投。带目标的"投 3"算投票、不算想开投 | `werewolf.onTick` 的白天分支 + `READY_VOTE_RE`；`#cfg().discussSeconds` → `create({ discussSeconds })` |
| **群里同时在闲聊别的话题** | 引擎只挑自己认识的两类消息（投票、"不玩了"这类退出指令），其余一概不看；模型照常参与闲聊（`hostBrief` 提醒别把闲聊当游戏动作） | 两个插件的 `onMessage` 只看匹配项 |
| **有人刷群消息** | 白天靠 `spoken` 集合去重（多说几句不重复计数、也不推进）；投票覆盖式（后到覆盖先到）；夜里群消息不参与任何判定 | 同左 |
| **有人一直不行动（AFK）** | 夜行动：90 秒窗口，超时按已收到的结算（空刀/不守/不查/女巫不用药）；白天：固定讨论时长（`discussSeconds`）；投票：`roundSeconds`。到点直接推进——**不点名、不刷"XX 没接上"**，没说过话也能投票；整局上限 `min(配置 maxDurationMin, 插件上限)` | `onTick` + Manager ticker |
| **结算要不要公布词/身份** | 控制台「结算时公开词与身份」开关现在真的生效（此前只有 UI 在读、引擎从不读，是死开关）：关掉后只报胜方，不列身份与夜晚记录 | `#cfg().revealWords` → `create({ reveal })` → `winEffect` / 卧底结算 |
| **女巫被狼刀了还能自救吗** | **不能**：狼刀落在女巫身上时，提示明确写"不能自救"，只给「不救 / 毒 3」两个选项；回「救」会被挡回并说明 | `werewolf.onPrivateMessage` 的女巫分支（`String(s.pending.killTarget) === uid` 判定） |
| **女巫同夜又想救又想毒** | **一晚最多用一瓶**：后到的覆盖先到的（先回「毒 3」再回「救」= 只救）；药水在夜晚结算时扣，用了就是用了 | 同上（`s.pending.witch` 单值覆盖） |
| **守卫守了 A、女巫又救 A** | **同守同救必死**（主流规则，防"双保险"让狼刀失效）；只守不救 / 只救不守照常活；毒药独立致命，可以一晚双死 | `resolveNight`（`savedOnce = guardedHit !== healUsed`） |
| **狼提交刀口后女巫已被告知，狼又改刀** | **拒绝**并回一句"刀口已经定下（女巫知道是谁了），今晚改不了啦"——否则女巫按旧刀口做的救/毒决定会失效 | 同上（`pending.killTarget` 锁定后的狼分支） |
| **出了局的人还在群里说话/投票** | **引擎一律不认**（狼人杀与卧底同口径）：发言不计入发言轮、`投 X` 不计票、`投吧` 不算想开投、不推动阶段，夜里说的更不看；出局那一刻会**私聊本人**说明"之后的发言与投票不再计入"。模型侧也被叮嘱只当遗言/围观：可以接话，但不把他的票当票、不顺着他说怀疑谁、不替他确认或否认身份（群里没人拦得住死人的嘴，能做的就是让判定不受影响） | `werewolf.onMessage` / `undercover.onMessage` 开头的 `!alive`/`eliminated` 直接返回 + `tally` 里的存活双闸 + `deathNotice()` / 卧底结算的私聊说明 + 两个插件的 `hostBrief` |
| **女巫死了/出局后会怎样** | 不再被问行动、也不能用药（药水随人作废）；白天在群里说「毒 X」不算行动——夜晚行动只认私聊 | `aliveOf(s, 'witch')` 空 → 不再发提示 |
| **女巫中途退出，本夜她已交过药** | 已交的药**作废**（人不在了药不生效、药水也不扣），其余行动齐了就直接结算 | `quitPlayer` 里 `if (target.role === 'witch') s.pending.witch = null` |
| **女巫两瓶药都用完（或只剩解药却被刀的是她自己）** | 这一夜不再等她回话（没有可选动作就不算欠行动），否则会白等 90 秒超时；提示文案按"还剩什么药"生成 | `nightReady` 的 `hasChoice` + `witchPrompt` 的被刀分支 |

## 5. 配置、开关与安全

```jsonc
{
  "groupGame": {
    "enabled": false,             // 实验特性，默认关（遵守 EXPERIMENTAL_FEATURE_STANDARD）
    "chats": ["group:123"],       // 白名单：只在这些群可开局（空=不开局）
    "games": ["number-bomb", "undercover"],  // 允许开局哪几种（控制台勾选；狼人杀要显式加进数组）
    "allowPrivateInvite": false,  // 是否允许私聊发身份/发牌（谁是卧底/狼人杀都需要；默认关）
    "allowGamePrivateDm": false,  // 游戏期间私聊豁免：只对在册玩家放宽 allow.private（默认关）
    "recruitSeconds": 45,         // 开局报名时长（0=不报名，直接按最近发言者发牌）
    "discussSeconds": 0,          // 白天讨论时长（0=插件默认 120 秒）
    "revealWords": true,          // 结算是否公开词/身份
    "maxPlayers": 10,             // 每局人数上限（与插件自身上限取较小值）
    "roundSeconds": 0,            // 单回合超时（0=插件默认；夜行动/投票用）
    "dailyLimitPerChat": 6,       // 每群每天最多开局数（防沉迷/防滥用）
    "maxDurationMin": 60          // 单局时长上限，到点自动结算
  }
}
```

- **风控**：私聊是唯一的"对外主动"行为——默认关闭；开启后只对**报名者**发、失败不重试。
  "每人每局 1 条"只对谁是卧底（发词）成立；狼人杀这类需要全程私聊行动的游戏按 §4.2 的
  游戏范围豁免走（只发在册玩家、只发引擎文本、局内有效）。参照好友退役一节的教训：
  绝不批量、绝不对非报名者发、绝不重试。
- **防卡局**：每个阶段都有窗口（夜行动 90 秒/人、白天 `discussSeconds`、投票 `roundSeconds`），
  到点由 ticker 推进；整局有 `maxDurationMin` 兜底；管理员 `stop` 随时可用。
  （"连续 3 次无人响应自动结束"没有单独实现——靠上面的窗口与兜底上限。）
- **实验特性流程**：走 `EXPERIMENTAL_FEATURE_STANDARD`（开关、默认关、观察后转正），
  控制台放"实验"页，转正标准 = 有真实群连续使用 2 周无卡局。
- **成本**：局内每轮只注入摘要（≤600 字符），回合唤醒走省 Token 上限；一局预算估算
  ≈ 20~40 次模型调用（远小于同时间的自由聊天）。

## 6. 实施步骤（含验收）

**M1（框架，2 天）**
1. `src/features/group-game.js`：Manager（生命周期、ticker、持久化、effects 派发）。
2. `group_game` 工具（start/stop/status）+ ctx 接线 + 提示词注入"进行中的游戏"段。
3. 插件：`games/number-bomb.js` → 端到端脚本测试（假时钟 + 假玩家驱动整局）。
4. 插件：`games/undercover.js` + 私聊发送通道（`sender.sendPrivate` 已有 → 走 `sendText('private')`）。
5. 测试：`test/group-game.test.mjs`（框架状态机 + 两个插件的正常/超时/中止/恢复路径，用注入 rng 与假时钟）。

**M2（体验与可运维，1.5 天）**
6. 控制台实验页开关 + 局内状态可视化（正在进行的局、强制结束）。
7. 战绩写记忆（可选）、每日局数上限、`daily-moments` 式调度统计日志。

**M3（更多游戏，按社区呼声）**
8. 狼人杀简化版 / 牌类；每个新游戏只写插件（框架不变）。

**验收标准（硬）**：① 一局完整跑通且中途重启能从 games.json 恢复；② 超时/无人响应/管理员中止
三条路径都有用例；③ 私聊只在 `allowPrivateInvite=true` 且对方报名后发送，失败不回退到群聊泄密；
④ 与普通聊天互不干扰（有局时聊天照常，提示词只多一段摘要）；
⑤ 狼人杀追加：夜晚行动只认在册玩家私聊、夜晚中途重启不重发提示、查验结果只达本人、
行动确认不经模型（drainUnread 生效）。

## 7. 风险清单

| 风险 | 缓解 |
|---|---|
| 私聊触发风控（历史上加好友实验的教训） | 默认关、只发报名者、每人 1 条、绝不重试（狼人杀的 DM 量级远超"每人 1 条"，走 §4.2 的游戏范围豁免：只发在册玩家、只发引擎文本、局内有效、dailyLimit 兜底） |
| 卡局（有人掉线/群冷掉） | 回合超时唤醒 + 连续无响应自动结束 + 时长上限 |
| 模型说漏身份 | 身份只走私聊，公开摘要不含隐藏信息（结构上不可能说漏） |
| 群友不按格式投票（"我投那个说豆浆的"） | 插件解析宽松匹配（序号/昵称/@），歧义时由模型主持澄清（话术层），判定仍由插件 |
| 状态膨胀 | 只留当前局 + 最近 1 局的结算摘要；games.json 原子写 |
| 与实验特性规范冲突 | 走标准流程：默认关、控制台开关、观察转正 |
| 夜晚行动依赖玩家私聊活跃度（AFK 不交行动） | 每个行动 90 秒窗口，超时空过（空刀/不守/不查）；连续整夜无人行动 → 自动结束 |
